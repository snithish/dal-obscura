# One product, one component system

This designbook imports the real application provider, fonts, theme and components.
It documents the executable R05 foundation and representative workflows; it is
not proof of a production-ready service.
Every identity and token shown here is synthetic. No real API or identity provider
is required. Keep this development server bound to loopback.

## Foundation ownership

`src/design/theme.ts` owns semantic colors and the Mantine theme. `AppProviders`
owns fonts and color-scheme management. `base.css` owns shared composition styles.
Use the toolbar for Light, Dark and System; System follows the operating system.
Use IBM Plex Sans for prose and controls, Mono only for code and identifiers.
Keep meaningful status text alongside Lucide icons; never rely on color alone.

<Canvas of={Foundations.Light} />

Use [Mantine components](https://mantine.dev/core/getting-started/) directly.
Do not create replacement Button, Input or Modal wrappers. Extract only repeated
domain compositions. Link upstream APIs instead of duplicating their prop docs.

## Patterns: errors and pending actions

Explain what failed and how to recover. Keep entered values after rejection.
Disable repeated submission while pending; unknown outcomes require reconciliation,
never a false success toast. Login stories verify retained input, retry dispatch,
pending submission and accessible error feedback in actual `LoginPanel`.

## Network boundary

The preview installs a cleanup-safe network guard. Stories reject `/v1/*`,
`/auth/*`, identity-provider, and other cross-origin requests immediately. Use
deterministic props and callbacks for component behavior; keep real API, IdP and
customer-data journeys in the application browser suites.

## Contribution acceptance

1. Reuse semantic tokens and the actual application component, not copied markup.
2. Document purpose, states, keyboard behavior, content and known limitations.
3. Add a play test only for a distinct product behavior. Keep algorithm tests in
   unit tests and actual authentication/network boundaries in Playwright.
4. Run `pnpm check`, `pnpm test:stories` and `pnpm build-storybook`.
5. Review both themes, 390px and 1440px widths, keyboard use and 200% zoom.
   Automated accessibility checks supplement human review.
6. Add no customer data, credentials, API proxies, remote fonts or IdP calls.
   The preview network guard enforces this boundary; reviewed visual baselines
   remain open E11 work and must not be replaced by networked stories.

Current executable coverage includes command search, authenticated shell states,
inventory and nested policy editing, stale review links, semantic history diff,
consumer handoff, access and grant management, connections and diagnostics,
runtime and identity settings, audit filters/pagination, lifecycle capability
guards, validation failures, and deferred-response recovery. These stories use
the production components and deterministic fixtures under the network guard.

Remaining acceptance gates are the full contrast matrix, reviewed responsive
visual baselines, manual keyboard/screen-reader/zoom review, owner visual
approval, and real backend/identity-provider journeys. Keep those checks in the
application browser and integration suites; never replace them with a story
fixture.
