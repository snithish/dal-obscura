# Bounded schema identity hashing

Measured on 2026-10-11, on the same arm64 Darwin 25.6.0 host, using CPython
3.12.10 and PyArrow 23.0.1. These are isolated installed-wheel microbenchmarks of
`schema_fingerprint`, not distributed read throughput or whole-worker RSS.

The baseline is commit `3cc1ff15`, with the lossless version-2 identity encoding.
The candidate retains that exact encoding, walks canonical objects iteratively,
and hashes chunks while enforcing the two-MiB canonical encoding budget. Small
scalar records are encoded together to avoid hashing every punctuation token.

The three fixtures are generated by
[the benchmark lane](../tests/benchmarks/test_schema_identity_benchmark.py).
They have fixed expected digests, so a faster or smaller but incorrect encoding
fails the benchmark. Timing and allocation probes are separate; fixture creation
is excluded from the allocation probe. Each timing case runs at least 15 rounds.
Reported latency is the median; garbage collection produces visible outliers in
both wide-schema runs.

- **4,000 string fields:** 7.680 → 10.692 ms; Python peak allocation
  2,605,265 → 902,625 bytes, about 65% lower. Median latency increases about 39%.
- **One depth-64 struct chain:** 1.133 → 1.587 ms; Python peak allocation
  147,454 → 51,355 bytes, about 65% lower. Median latency increases about 40%.
- **1,200,000 metadata bytes:** 3.990 → 4.236 ms; Python peak allocation
  5,203,321 → 4,401,316 bytes, about 15% lower. Median latency increases about 6%.

This trades CPU for predictable canonical encoding admission and less retained
Python representation. It is not a universal speedup. Arrow serialization,
metadata byte copies/base64 conversion, and native type rendering still allocate.
The canonical byte budget is not a process-memory cap. Deep provider execution,
IPC beyond the current depth limit, UI rendering, concurrent workers, and live
cloud IO were not measured here.

Both wheels are version 0.2.0, distinguished by immutable artifact hashes:

- Baseline service SHA-256:
  `fa1d9a1f9784e7eaa55cf0ac3f53596394a90afda838d5faf3c13c08ed755603`.
- Candidate service SHA-256:
  `160b93e736dac638784e3a591950b5b679e1798e2de569dc80e05837c20dd28d`.

Each fresh environment contains the same 102 pinned dependencies and unchanged
SDK, conformance, bundled format/catalog, and native reader wheels. Production
imports come from installed wheels, with repository source paths disabled.
Artifacts and raw benchmark JSON are outside Git. See
[plugin qualification](plugin-rebuild.md) for wheel installation and lock creation.

Commands used after other test processes finished, run sequentially:

```bash
uv run --no-project --python /tmp/dal-metadata-wheel-env/bin/python python -m pytest -o pythonpath= tests/benchmarks/test_schema_identity_benchmark.py --benchmark-only --benchmark-json=/tmp/dal-schema-hash-before.json -q
uv run --no-project --python /tmp/dal-schema-hash-wheel-env/bin/python python -m pytest -o pythonpath= tests/benchmarks/test_schema_identity_benchmark.py --benchmark-only --benchmark-json=/tmp/dal-schema-hash-after.json -q
```

Reproduction requires recreating those fresh environments from the corresponding
artifacts. Run the same checked-in benchmark module against both environments;
never compare source imports with installed imports or trace allocations during
the timing run.
