S3 · Nested governance · Distributed Flight

Follow one governed read.
Verify every returned row.

A catalog with 101 real tables. One deeply nested target. Deletes and replacement updates remain in merge-on-read form. Three independent Flight workers fetch disjoint tasks and apply seven PII masks.

The default fixture has 10 × 1,000,002 physical base rows. After the permanent delete, every partition still has at least 1,000,000 live rows. These exact sizes fit Delta’s current snapshot-wide deletion-vector budget; the limit is documented below.

Evidence environment: a Docker Compose S3 API emulator and PostgreSQL catalog/database. Reads use the real Delta, Iceberg, Arrow, DuckDB and Flight libraries. This demonstrates worker-independent execution and S3 semantics; it does not establish AWS throughput or a multi-host speedup.

Public directory keys and labels remain readable. A PII key cannot be null inside an Arrow map: the policy compiler hides that map entirely. Null containers, empty containers and null elements are distinct expected values.

What changes in storage?

Show an independently checked output sample
Rows repeat eight null/empty cases throughout all partitions. The scalar oracle reconstructs synthetic source values and masks them independently of the production projection compiler.
A bug found by this scenario: PyIceberg 0.11.1 rebuilds struct-valued lists/maps without the original validity bitmap. Nulls became empty collections both on writing and schema evolution. The production read bridge now restores validity; sliced nested Arrow columns are also compacted at the DuckDB boundary to prevent offset/null misreads. Plugin execution uses the captured stream/ticket deadline instead of the planning timeout. Fixture Parquet is written by Arrow and committed through PyIceberg’s public add_files API. Stored and native-reader values were checked separately before the fix.



03 / Work placement
Data ownership travels with the ticket.
Planning groups disjoint work under a three-task budget. Each worker receives one signed ticket through Flight and independently reopens the pinned snapshot with its own S3 credentials. The example’s client schedules concurrent fetches explicitly; the standard Python convenience iterator is sequential.
Live rows by physical partition · pinned read
Owned data, shared metadata
The emulator denies a worker’s GET of a data file outside that ticket’s file set. Metadata and delete files may be shared. Exact ID coverage and non-overlapping task units prove work ownership beyond this file-level guard.
Stateless fetch
HMAC token → shared ticket record → principal/context/expiry verification → admitted plugin/artifact → captured task. The worker does not re-resolve the catalog or substitute a newer policy. PostgreSQL reserves the exchange atomically before execution.
This Compose run uses separate processes/containers on one VM. The same passive contracts can cross hosts; cluster scheduling, remote deployment and cluster throughput are outside this example.

Plan latency ends when FlightInfo arrives. First-batch latency is plan latency plus the earliest worker batch. Total read time is plan latency plus the wall time of all parallel fetches. Appending after planning, ticket introspection and S3 controller setup are outside that sum.

Execution configuration
Arrow/native allocations are not all charged to DuckDB. These are per-stream/process admission limits, not a hard RSS or cluster-capacity guarantee. Byte checks occur after allocation.



05 / Verify, don’t assume
Which optimizations actually happen?
A returned row count cannot prove storage pruning. The partition probe asks for partition = '3'; the projection probe asks only for id. The evidence below compares native task coverage, S3 data paths, HTTP ranges and response bytes against the warm full read.

GET bytes sum HTTP Content-Length on successful data GETs, including repeats/footer reads. They are response body bytes, not unique stored bytes or total wire traffic. File ownership guards do not restrict byte ranges within an assigned file.
Partition pruning is currently absent. Both bundled format descriptors omit filter_pushdown. Core sends no SQL hint; a partition predicate is evaluated by DuckDB after native reading. The probe verifies correct output but shows the storage work still covers every partition. The HTML records that gap explicitly; adding pruning is a separate production change that must retain the complete residual filter.

06 / Independent assertions
Correctness is more than a row count.
Repository qualification: 1,076 Python tests passed with real consumer backends and disposable PostgreSQL, zero skips. Fresh installed-wheel qualification: 227 passed with repository Python paths disabled, plus both official FileIO transport cases. Ruff and type checks passed. These lanes complement the large scenario assertions below.
Completed checks
How the result can fail
  • A duplicate, missing, deleted or out-of-range ID fails a bounded coverage bitmap.
  • Any wrong nested scalar, collection shape or output metadata fails exact comparisons.
  • The updated ID must occur once. Its unmasked event/directory label proves the replacement row is read, rather than merely hiding its changed email.
  • An append after planning must remain invisible to old tickets and visible to a fresh plan.
  • Any unrelated data GET, denied ownership GET or server failure fails IO assertions.
  • A caller predicate on masked PII must be denied, preventing a filter side channel.
  • For full-size reads, every physical partition must retain ≥1,000,000 live rows.
The fixture writer is not the expected-result implementation. Delete metadata is generated using owning test helpers; read protocol interpretation remains with maintained libraries. This scenario complements, rather than replaces, cancellation, security and installed-wheel lanes.

08 / Honest boundaries
What this evidence does—and does not—establish.
Maintained engines own protocol semantics
Both COW and MoR use the same format contract. Delta transports use official delta-rs object storage; Iceberg uses official PyIceberg FileIO through a read-only native adapter. Each range opens/closes a provider stream and copies bytes across Python/Rust. Catalog selection is independent of task execution; provider dependencies and worker credentials remain required.
Delta-rs/Delta Kernel reconcile the pinned transaction log and decode deletion vectors. Arrow scans assigned row groups. Apache Iceberg Rust plans and reads files/ranges with position/equality deletes and sequence rules. PyIceberg owns catalog commits, FileIO, metadata and field-ID evolution; DuckDB owns SQL filters/masks.
Fixture-only gaps: public PyIceberg does not expose this equality/position delete writer, so the owning fixture helper writes delete Parquet and uses its upstream Avro manifest machinery. Arrow add_files avoids the known struct-collection write bug. Delta fixture commits use unsafe rename only against the disposable emulator; that setting is not a production S3 concurrency recommendation.
Delta-rs documentation · PyIceberg API · Apache Iceberg Rust · Upstream projection visitor
Measured limits
  • S3 is Moto over HTTP in a private network; TLS/IAM/KMS, AWS latency and service quotas are unqualified here.
  • JWT issuance is synthetic. Signature/issuer/audience validation is real; federated SSO/logout is not covered.
  • Ten million base rows and ten partitions are exercised. Larger DV snapshots may fail the current explicit cap.
  • One VM, separate stateless worker processes. No distributed-host speedup or single-worker comparison is claimed.
  • Metadata/footer/delete reads can repeat per worker. Iceberg currently reads all snapshot fields before selecting output; Delta has column projection but no predicate pruning.
  • Output batch telemetry is exact; native RSS, cluster memory and end-to-end deployment capacity are not measured.
